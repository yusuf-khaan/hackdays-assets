05 / 08
trap 1

You hashed the parsed JSON, not the raw bytes.

bytes the sender signed
{"type":"payment.succeeded","amount":499}
bytes after parse + re-stringify
{"type": "payment.succeeded", "amount": 499}
Same data. Two extra spaces. A completely different hash. Real events start failing, and someone “temporarily” switches the check off.
Hash the raw body. Then don’t compare it with ==…

trap 2

A plain == can leak how much of the guess was right.

verify.js
// stops at the first wrong character
if (sig == expected)

// takes the same time either way
crypto.timingSafeEqual(
  Buffer.from(sig), Buffer.from(expected))
GitHub’s docs say it directly: compare signatures with a constant-time function.
Now the check is right. A valid signature can still hurt you…

// the replay

Someone captures one real, signed request. And sends it again.

signed 14:02
accept
5-minute window
resent 16:40
reject
Stripe signs a timestamp together with the body. Its libraries reject events older than 5 minutes by default.
And keep each event ID you’ve handled, so a genuine resend is processed once.

// lab notes · every webhook endpoint

Three checks before you trust the payload.

[01]HMAC of the raw body with your secret
[02]Compare in constant time
[03]Fresh timestamp + event ID not seen before
Fail any one: return an error, change nothing.
Save this for the next webhook you wire up.
